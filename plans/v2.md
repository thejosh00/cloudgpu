# cloudgpu v2 plan

**Status:** proposed, 2026-11-06. No phase has started.

## Goal

`cloudgpu up <config>` gets a working machine as soon as any acceptable GPU exists, in any
region, with your apps, models and work in place. Replacing a machine should be routine and
should never lose work or leave one running unnoticed.

The main problem to solve is capacity waits. A filesystem is tied to one region, so `up` only
looks for GPUs there and can wait up to `max_hours` (12 by default).

This is a series of incremental changes, not a rewrite. The design of disposable machines plus
persistent storage stays.

## Non-goals

- Support for other cloud providers
- A control-plane service or web UI
- A move to containers
- A rewrite in another language or framework

|---|---|---|---|

| 3 | Data sync to your own bucket | M | 2 |

The capacity logger goes near the front of the build order, because it needs time to collect data while
the other work goes on.

## How this gets built

The same pattern as otto's `otto-build` and `otto-driver`:

| Who | Does | Never does |
|---|---|---|
| **`cloudgpu-driver`** | Hands off one item at a time, checks each independently after it lands, keeps this plan true ([`workflows/drive-flow.md`](../workflows/drive-flow.md)) | Writes code, approves, lands, pushes, or spends money |
| **`cloudgpu-build`** | Builds each item and sends it back as a change ([`workflows/build-flow.md`](../workflows/build-flow.md)) | Pushes, or spends money |
| **You** | Review every change, make decisions D1–D5, run every on-instance check | |

**The loop:** the driver writes an item into `~/workspace/cloudgpu-queue/`; the builder builds it and sends
you a change; you approve; the lander lands it; the builder verifies it; the driver checks it again from
cold, then hands off the next.

**How it differs from otto:**

- **Handoff:** `otto state assign` only files work in otto's own queue, and only one run can be its driver.
  So the pair uses a file queue, like `architect-build`.
- **Installing:** `cloudgpu` is an editable install of the main checkout, so landing also installs. There's
  no install or rollback step.
- **Live tests:** real checks need a billed GPU instance, so neither agent runs them. The driver batches
  on-instance checks per phase and gives you the commands.

**The API key:** `LAMBDA_API_KEY` is exported from `~/.zshrc`, and wakes run with permissions bypassed, so a
wake could very likely launch or terminate instances and delete filesystems. Step 0 below hides it from wakes,
and each wake stops if it can still see the key. That prevents accidents, but it isn't a security boundary: an
unsandboxed agent could still read `~/.zshrc`. Only a sandbox enforces this, so move these runs into one when
otto's sandbox work is ready.

### Starting it

Run these from the repo root, after committing `plans/` and `workflows/` to `main`, because the driver reads
the plan from `origin/main`.

```bash
# 0. In ~/.zshrc, replace the plain export so wakes don't get the key. otto sets OTTO_RUN_ID in every wake.
#      if [[ -n "$OTTO_RUN_ID" ]]; then unset LAMBDA_API_KEY; else export LAMBDA_API_KEY=<your existing value>; fi
#    Then open a new terminal and confirm it works. The first command should print "present", the second "absent":
zsh -lic 'if [ -n "${LAMBDA_API_KEY+x}" ]; then echo present; else echo absent; fi' | tail -1
OTTO_RUN_ID=test zsh -lic 'if [ -n "${LAMBDA_API_KEY+x}" ]; then echo present; else echo absent; fi' | tail -1

mkdir -p ~/workspace/cloudgpu-queue

# 1. The builder. Its first wake finds an empty queue.
otto run --name cloudgpu-build --instructions workflows/build-flow.md \
  --repo "$PWD" --repo ~/workspace/cloudgpu-queue --perpetual --period 15m --budget-tokens 100M \
  --goal "Build cloudgpu from ~/workspace/cloudgpu-queue, one item at a time. Never push: every item goes back as a change for me to approve. Never spend money or touch real Lambda resources. Every fix has a test that fails without it. Ask me if an item is unclear or disagrees with plans/v2.md."
otto check cloudgpu-build --script workflows/build-check.sh --wake-after 96

# 2. The driver. Its first wake reads the plan and writes its todo.
otto run --name cloudgpu-driver --instructions workflows/drive-flow.md \
  --repo "$PWD" --repo ~/workspace/cloudgpu-queue --period 15m --budget-tokens 100M \
  --until "Every item in plans/v2.md is done or set aside with a reason I have seen, and every line of its Done means section holds" \
  --goal "Carry plans/v2.md to done, one item at a time, through cloudgpu-build. Hand off one item by writing it to ~/workspace/cloudgpu-queue, and the next only after checking the last one yourself from cold. Never write cloudgpu's code, and never approve, land, push or merge anything. Never spend money or touch real Lambda resources: on-instance checks are mine to run. You may change plans/v2.md when the work shows it is wrong, but only as a change for me to approve, and hand off nothing while one waits on me. A check that fails stops the work and comes to me."
otto check cloudgpu-driver --script workflows/driver-check.sh --wake-after 96
```

**To pause it:** `otto pause cloudgpu-driver`. The builder finishes what's out, then has nothing to do.
**To end it:** `otto stop cloudgpu-driver` and `otto stop cloudgpu-build`.

**Budgets:** 100M each is a rough estimate. `otto-build` has used about 2.7M a wake. When a run reaches its
budget it stops on a question, and you can raise it then with what you've learned about the real cost.

## Done means

- After any termination, `cloudgpu up <config>` restores the full machine with no extra flags.
- A file planted in an app's venv does not execute as `ubuntu`, shown on a real instance.
- Your work survives a termination, including one by the billing guard, shown on a real instance.
- Unless phase 5 was a no-go, `up` reaches a machine in another region when the home region has no capacity,
  shown on a real instance with its time and cost recorded.
- An idle instance terminates, and a long job isn't killed for being idle.
- Each phase's "Done when" holds, and nothing is still listed as unverified.

| Bug | Where | Fix |
|---|---|---|
| App code can reach `ubuntu`, and so the Lambda key. `cloudgpu-app` can write the venv, and `check_torch_cuda` runs that venv's Python as `ubuntu` on every `status` and `up`. | `remote/utils.py` (`check_torch_cuda`), `remote/apps/comfyui.py:171,195`, the same pattern in `aitoolkit.py` | Run app-venv checks as `cloudgpu-app`. - The on-instance R3 checks, which still haven't been run, are run on a real instance. That run

## Phase 1: Capacity logger and go/no-go check

Failover only helps if GPUs are often free in other regions while the home region has none.
Measure that before building phase 5.

- `cloudgpu capacity log`: takes one sample of `list_instance_types` and appends the timestamp,
  type and available regions to `~/.local/state/cloudgpu/capacity.jsonl`.
- `cloudgpu capacity report`: for each config and GPU list, shows how often the home region had
  capacity, how often only other regions did, how often none did, and which regions are most
  often available.
- Run a sample every 5 minutes for at least 1–2 weeks. The sampler holds a real API key, so you start it
  yourself (item 1.3), outside any agent.

**Go/no-go for phase 5:** go if at least 25% of samples have no capacity in the home region but
some elsewhere. That threshold is a starting suggestion, so adjust it once you see real data.
If the result is no-go, phases 0, 2, 3, 4 and 6 are still worth doing.

## Phase 2: Convergent `up`

- Add `profiles = [...]` to the config, so `cloudgpu up small` always means the same thing. `-P`
  remains as a one-off addition.
- Each `up` follows the same steps: find or launch the instance, set it up, arm the cap, make
  apps match, provision, restart services, verify, report.
- Make the local state file safe: write it atomically, and report corruption instead of
  treating it as empty (`configs.py:128-140`).
- Report `up` as successful only if the expected services are active.

**Done when:** after any termination, `cloudgpu up <config>` restores the full machine with no
extra flags. Interrupting `up` at any step and re-running it finishes the job without a second
instance.

## Phase 3: Data sync to your own bucket

The filesystem becomes a cache, and the bucket becomes the source of truth for your work.

| Data | Examples | Handling |
|---|---|---|
| Rebuildable | Apps, venvs, Node, bin scripts | Rebuild |
| Re-downloadable | Models, HF cache | Re-run provisioning |
| Irreplaceable | Outputs, trained LoRAs, datasets, saved workflows | **Sync to the bucket** |

**Paths:** leave files where they are, so nothing that reads them today breaks. Each app declares
its default sync paths, and a profile can add more. Confirm the real paths on an instance;
the expected ones are ComfyUI's `output/`, `input/` and `user/`, and ai-toolkit's datasets and
training outputs.

```toml
[sync]
remote = "r2:cloudgpu/small"   # rclone remote and prefix
interval_minutes = 5
extra_paths = []               # relative to the persistent dir
```

**Behaviour:**
- A timer on the instance runs `rclone copy`, not `rclone sync`, so a deletion on the instance
  can't delete anything from the bucket.
- Restore runs before services start. A failed restore fails `up`.
- `down` does a final sync first. If it fails, it asks before terminating; `-y` needs an explicit
  `--skip-sync` to continue.
- The billing guard also does a final sync, limited to 10 minutes. **Stopping the bill wins:** after
  the limit it terminates anyway and logs the failure, so at worst you lose work since the last
  successful sync.
- `status` shows the time of the last successful sync, and warns when it's stale.

**Security:** use a key limited to this bucket, passed as file content and never on a command line,
stored root-only on instance-local disk, and unreadable by `cloudgpu-app`. Run the sync as a
dedicated user with read access through the group. Leave symlinks unfollowed so app code can't
point the sync at other files.

**Done when:** on a real instance, a file created in each declared path reaches the bucket and is
restored onto a new, empty filesystem, and a forced guard termination still does its final sync.

## Phase 4: Per-architecture, pinned environments

Both configs mix arm64 (GH200) with x64 (A100/H100) but share a venv, so changing architecture
deletes and rebuilds it. Failover would make those changes more common.

- Use `venvs/<arch>/<app>`, as ai-toolkit's Node install already does. Migrate existing venvs in
  place by moving them under the architecture that built them.
- Pin the ComfyUI and ai-toolkit commits, plus custom node revisions, with explicit commands to
  upgrade them. Stop running `git pull` during `install`.
- Store a lock of the working Python packages per architecture.
- Make the venv read-only to `cloudgpu-app`. **Tradeoff:** ComfyUI-Manager can no longer install
  dependencies at runtime, so those installs must go through provisioning. Test this with the
  nodes you use before committing to it.

**Done when:** moving between GH200 and A100 doesn't rebuild an environment that already exists
for that architecture, and two fresh installs from the same pins resolve to the same packages.

## Phase 5: Region failover

Only start after phase 1 gives a go.

### Config

```toml
gpu = ["gh200", "a100"]
failover_after_minutes = 10    # unset = stay in the home region, as today
regions = []                   # optional allow-list; empty = any region
```

Failover is opt-in, and it's refused unless `[sync]` is configured. Otherwise your work would look
lost after a move, even though it would still be on the old filesystem.

### Region selection

A **warm** region already has this config's filesystem. A **cold** region doesn't.

```
on each poll, using capacity for all regions:
  1. Any acceptable GPU in a warm region -> launch there (GPU preference order breaks ties)
  2. After failover_after_minutes, any acceptable GPU in a cold region -> create filesystem, launch
  3. Otherwise keep polling until max_hours
```

Any GPU in a warm region beats a preferred GPU in a cold one, because it starts much faster.

### Filesystem naming

- New filesystems are named `<config>-<region>`.
- A filesystem belongs to a config if it's named in the config, or if its name matches
  `<config>-<region>` **and** its region field equals that suffix. The second check stops `small`
  from claiming a filesystem belonging to a config called `small-us`.
- Existing filesystems (`small`, `lora`) keep working, and count as warm in their region.
- State records the filesystem in use, and code reads it from state, not from `cfg["filesystem"]`.

### Required code changes

| Where | Change |
|---|---|
| `orchestration.py:194-235` | Add warm and cold selection. Stop locking to a region before a launch succeeds. If a launch fails on a filesystem created for it, delete that empty filesystem and unlock. |
| `cli.py:713,755` | Use the chosen filesystem. |
| `cli.py:432-441` (`_instance_mounting`) | Check all of the config's filesystems. Keep the rule of one running instance per config. |
| `cli.py:907-965` (`down`) | Handle a set of filesystems. `--delete-filesystem` lists exactly what it will delete before confirming. |
| Remote setup | Restore from the bucket before services start. |

### Failure handling

- Arm the billing cap before any slow step, as `up` does today.
- If setup fails in a cold region, stop and report. Don't automatically try another region, because
  that could repeat a paid failure. The billing cap still applies to the instance left running.
- If a warm region gets capacity during a cold-region setup, carry on. Switching would waste the
  work already done.

### Cost controls

- `up` prints why it chose the region and whether it's a cold start, plus the running price.
- `cloudgpu fs list` shows each filesystem's region and when it was last used.
- `cloudgpu fs prune` removes filesystems unused for a set time. It always lists them and asks
  first, and it refuses if the last sync can't be confirmed as successful.
- Later, use the phase 1 data to keep two regions warm, so most moves avoid a cold start.

**Done when:**
- Unit tests cover warm over cold, the grace period, the allow-list, a lost launch race, name
  ownership, and refusal without `[sync]`.
- A real test with the home region excluded through `regions` reaches a cold region, restores
  your data, and serves ComfyUI. Record the time and cost of that cold start.
- Running `up` again adopts that instance and doesn't launch another.

## Phase 6: Idle-based billing guard

Today's fixed deadline can stop a running job, which is why `autoterminate` has to be extended by
hand during training.

- Terminate after `idle_terminate_minutes` of no activity, keeping `auto_terminate_hours` as a
  hard ceiling that always applies.
- Activity means GPU use above a threshold, or a non-empty ComfyUI queue, or a running ai-toolkit
  job.
- If activity can't be read, treat the instance as idle only once the hard ceiling is reached.
  A broken check must not terminate a job early or remove the ceiling.
- Enable a default cap on new configs, since a forgotten instance is the costliest failure.
- Keep the guard standalone and stdlib-only, as `remote/autoterminate.py` is today.

**Done when:** a long training job survives past the idle window, an idle instance terminates,
and the hard ceiling still fires during constant activity.

## Phase 7: Model manifest (optional)

Failover does **not** need this, since `provision.py` can already fill an empty filesystem. Build it
if cold starts or corrupted downloads turn out to be a real problem.

- List each model's repo, file, revision, destination and SHA-256 in TOML. `provision.py` stays for
  anything unusual.
- This adds disk-space checks, cold-start estimates, pinned revisions, and integrity checks (a
  file now counts as present if it's non-empty; `comfylib.py:87`).
- It also replaces the `comfylib.py` copies vendored into each profile.

## Testing

- `pytest` covers the logic, with the API and SSH mocked. It can't prove behaviour on an instance.
- Each phase's on-instance checks need a real GPU instance, which costs money. Group them into one
  session where possible.
- Report any on-instance check that wasn't run as **unverified**, never as passed.
